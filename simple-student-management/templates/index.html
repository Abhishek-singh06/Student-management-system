🔬 Normalization Verification & Relational Proof

Mathematical and theoretical confirmation that this schema conforms to Third Normal Form (3NF)

1NF

First Normal Form (Atomicity)

All column values are atomic (indivisible scalars). Every record has a unique row identifier (surrogate primary key id), eliminating repeating groups.

✅ Satisfied: Atomic scalar types, discrete rows, unique candidate keys.
2NF

Second Normal Form (No Partial Dependency)

Database is in 1NF and contains no partial dependencies: all non-key attributes depend fully on the primary key. Since primary keys are single-column integer IDs, partial key dependency cannot exist.

✅ Satisfied: Every non-prime attribute depends on the full primary key.
3NF

Third Normal Form (No Transitive Dependency)

Database is in 2NF and contains no transitive dependencies (X → Y → Z). Department details (name) are isolated into departments, preventing student records from repeating branch descriptions.

✅ Satisfied: Transitive anomalies eliminated via foreign key relationship.

SQLite DDL Schema Definition (Executable SQL)

-- Enforce Referential Integrity in SQLite (Strict FK validation)
PRAGMA foreign_keys = ON;

-- 1. Departments Table (Parent Entity)
CREATE TABLE IF NOT EXISTS departments (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT UNIQUE NOT NULL
);

-- 2. Students Table (Child Entity)
CREATE TABLE IF NOT EXISTS students (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    registration_number TEXT UNIQUE NOT NULL,
    full_name TEXT NOT NULL,
    email TEXT UNIQUE,
    department_id INTEGER,
    year_of_study INTEGER CHECK (year_of_study BETWEEN 1 AND 4),
    cgpa REAL CHECK (cgpa >= 0.0 AND cgpa <= 10.0),
    subjects TEXT,
    phone_number TEXT,
    FOREIGN KEY (department_id) REFERENCES departments(id) ON DELETE SET NULL
);

-- Index for optimizing Foreign Key Lookups & Joins
CREATE INDEX IF NOT EXISTS idx_students_dept ON students(department_id);

🎓 DBMS College Viva & Review Defense Cheatsheet

Essential theoretical and implementation questions commonly asked by professors during database project vivas

1. Why SQLite instead of MySQL or PostgreSQL?
SQLite is a self-contained, serverless, zero-configuration, ACID-compliant transactional SQL database engine. The entire database resides in a single cross-platform disk file (students.db), eliminating network socket overhead and administrative server setup for a standalone academic application.
2. Why use a Surrogate Key (id) alongside Natural Key (registration_number)?
The surrogate integer primary key (id) provides high-performance fixed-width indexing and stable foreign key references. The natural key (registration_number) is enforced via a UNIQUE NOT NULL constraint to guarantee domain-level real-world uniqueness without making foreign keys bulky text strings.
3. How is Referential Integrity enforced in this project?
By default, SQLite maintains foreign key compatibility with legacy databases by disabling checks. Our backend explicitly runs PRAGMA foreign_keys = ON; on every database connection. The constraint ON DELETE SET NULL ensures that if a department is deleted, enrolled students remain in the database with department set to NULL rather than orphaned or accidentally wiped.
4. How does the application defend against SQL Injection?
All backend queries in app.py utilize parameterized queries (? placeholders) via the Python sqlite3 driver. Input parameters are transmitted separately from the SQL statement logic, preventing malicious SQL payloads from escaping input strings.
5. How does this system uphold ACID Properties?
Atomicity: Transactions commit completely or roll back on error. Consistency: Schema constraints (CHECK, UNIQUE, FK) are validated before commit. Isolation: SQLite uses write-ahead logging (WAL) or serialized locking. Durability: Once committed, changes are flushed to disk in students.db.
6. What is the role of CHECK and Domain Constraints?
Domain constraints like CHECK (year_of_study BETWEEN 1 AND 4) and CHECK (cgpa BETWEEN 0.0 AND 10.0) enforce business rules directly at the relational storage layer, guaranteeing database validity regardless of which application client executes the write operation.
